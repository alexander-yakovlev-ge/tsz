# План работ: сайт ТСЖ

Основа — ТЗ v1.13 ([requirements.md](requirements.md)). Этап 0 (сверка модели с выпиской из реестра) выполнен.

**Главное правило:** этап считается завершённым, только когда его результат развёрнут локально в Docker с нуля и прошёл проверку (разд. 1). Следующий этап не начинается, пока предыдущий не принят.

---

## 1. Как проверяется каждый этап

### 1.1 Протокол приёмки
Порядок одинаковый для всех этапов. Команды появляются на этапе 1 в виде `Makefile`.

| Шаг | Команда | Что проверяется |
|---|---|---|
| 1. Чистое окружение | `make reset` | `docker compose down -v`: удаляются контейнеры, тома БД и хранилища |
| 2. Сборка и запуск | `make up` | `docker compose up -d --build`: образы собираются, все сервисы переходят в `healthy` |
| 3. Миграции и seed | выполняются автоматически при старте `api` | `prisma migrate deploy` + seed без ошибок |
| 4. Тестовые данные | `make fixtures` | Синтетические данные этапа загружаются (разд. 1.3) |
| 5. Автотесты | `make test` | Модульные и интеграционные тесты внутри контейнеров |
| 6. E2E | `make e2e` | Playwright в отдельном контейнере проходит сценарии этапа на развёрнутом стеке через Caddy |
| 7. Smoke | `make smoke` | Скрипт проверяет health, ключевые страницы на 3 языках, коды ответов |
| 8. Ручная проверка | чек-лист этапа | Сценарии из раздела этапа «Ручная проверка» в браузере на `https://localhost` |
| 9. Перезапуск | `make restart` | После `docker compose restart` данные сохраняются, сервисы снова `healthy` |

Результат приёмки фиксируется в `docs/acceptance/stage-N.md`:
- дата и коммит;
- вывод `make test` / `make e2e`;
- отмеченный чек-лист;
- найденные проблемы.

### 1.2 Требования к окружению
- Нужны только Docker и Docker Compose. Node и pnpm на машине разработчика не обязательны: всё собирается и запускается в контейнерах.
- Сайт открывается по `https://localhost`: Caddy выпускает локальный сертификат (`tls internal`). Корневой сертификат Caddy один раз добавляется в доверенные.
- Порты наружу:
  - 443 — Caddy;
  - 8888 — веб-интерфейс filer SeaweedFS (просмотр файлов), только на 127.0.0.1.
  - БД наружу не публикуется.
- Секреты — в `.env` (не в git). Шаблон — `.env.example`.

### 1.3 Тестовые данные
Реальная выписка и персональные данные в репозиторий не попадают. Вместо них — **генератор синтетических данных** (`scripts/fixtures`). Он воспроизводит структуру выписки:
- 312 помещений с кадастровыми кодами нужного формата: 259 квартир, включая номера 5ა–5დ и объединённые 132 и N228 (код 502), 47 машиномест, 5 коммерческих, 1 техническое;
- вымышленные собственники:
  - физлица и 1 юрлицо с 15 помещениями;
  - совладельцы и доли, включая «долю внутри доли»;
  - дубли с разным написанием;
  - однофамильцы;
- файл `registry.csv` в формате п. 8.10 ТЗ, у части собственников — телефон;
- «новая выписка» с изменениями для проверки синхронизации.

## 2. Этапы

Размер этапа: S — несколько дней, M — 1–2 недели, L — 2–3 недели.

### Этап 1. Инфраструктура и каркас (M)
**Цель:** пустое, но рабочее приложение, которое поднимается одной командой.

Задачи:
- Монорепозиторий pnpm: `apps/web` (Next.js), `apps/api` (NestJS; воркер — точка входа `src/worker.ts` в том же образе), `packages/shared`.
- Dockerfile для каждого приложения: multi-stage, итоговый образ без dev-зависимостей.
- `docker-compose.yml`:
  - сервисы `proxy` (Caddy), `web`, `api`, `worker`, `postgres`, `storage` (SeaweedFS);
  - healthcheck у каждого сервиса, `depends_on: condition: service_healthy`.
- `docker-compose.dev.yml`: hot reload через bind-mount для разработки.
- `/api/health`: проверяет доступность БД и S3-хранилища.
- Prisma: начальная миграция, автоматический `migrate deploy` при старте `api`.
- Seed: администратор (из `.env`), `Contact`, `HomePage`, категории документов.
- Бакет хранилища создаётся автоматически при старте.
- `Makefile`: `up`, `down`, `reset`, `restart`, `logs`, `test`, `e2e`, `smoke`, `fixtures`, `psql`.
- Контейнер Playwright для e2e, скрипт smoke.
- ESLint, Prettier, typecheck. `make check` запускает всё в контейнере.
- Генератор синтетических данных (разд. 1.3) — каркас, наполняется по этапам.

Проверка:
- Автоматически:
  - `make reset && make up`: все сервисы `healthy` за разумное время;
  - `/api/health` → 200;
  - e2e: главная открывается через `https://localhost`.
- Вручную:
  - в логах `api` видны применённые миграции и seed;
  - интерфейс filer SeaweedFS (`http://127.0.0.1:8888/buckets/`) открывается, бакет `files` создан;
  - `make restart` не теряет данные БД.

### Этап 2. Авторизация, роли, мультиязычность (M)
**Цель:** вход, сессии и защита страниц на трёх языках.

Задачи:
- Модель `User`: роли, `token_version`, мягкое удаление.
- `/api/auth/login|logout|session`: JWT в httpOnly-cookie, скользящее продление, проверка `token_version`.
- Rate limiting входа: 10 попыток за 15 минут с одного IP.
- Проверка `Origin` на мутирующих запросах.
- next-intl:
  - префиксы `/ka|ru|en`, редирект без префикса;
  - исключения для `/api`, статики, `sw.js`, manifest.
- Middleware защиты `/admin/*` и `/account/*`, возврат на исходную страницу после входа.
- Каркас вёрстки: шапка, меню, переключатель языка, адаптивность.
- Админка-оболочка, дашборд-заглушка.
- Смена пароля (`/account/change-password`), раздел «Пользователи» (CRUD, сброс пароля).
- AuditLog: модель и запись событий авторизации и пользователей.

Решения (ТЗ v1.7):
- скользящее продление выполняют и API, и middleware Next.js;
- нельзя удалить себя и снять с себя роль ADMIN;
- `/account/*` доступен всем, кто вошёл; `/account` без помещений показывает только ссылки;
- временный пароль менять при первом входе не обязательно;
- в меню только работающие разделы;
- привязка учётных записей к собственникам — на этапе 4, когда появится модель `Owner`;
- тестовый API (`ENABLE_TEST_API`) для e2e: сброс лимита входа;
- оформление — вариант C (фото дома, Manrope + Noto Sans Georgian, акцент `#0f766e`).

Проверка:
- Автоматически:
  - e2e: вход админа;
  - неверный пароль → общее сообщение;
  - 11-я попытка → 429;
  - `/ru/admin` без сессии → `/ru/login`, после входа возврат обратно;
  - смена роли или сброс пароля сразу завершают чужую сессию;
  - `/admin` → редирект на язык браузера;
  - интеграционный тест: запрос с чужим `Origin` отклоняется.
- Вручную:
  - все страницы этапа на трёх языках;
  - вёрстка на ширине телефона;
  - cookie с флагами `HttpOnly`, `Secure`, `SameSite=Lax`.

### Этап 3. Публичный контент (M)
**Цель:** публичная часть сайта и её администрирование.

Задачи:
- Главная из `HomePage` (Markdown), раздел `/admin/home`.
- Контакты: `/contacts`, `/admin/contacts`, блок контактов на главной (ТЗ v1.8, п. 6.5):
  - телефоны председателя и контактного лица ведут в чат WhatsApp;
  - необязательные ссылки на каналы ТСЖ в WhatsApp и Telegram, `whatsapp_url` — новое поле.
- Объявления:
  - закрепление, отложенная публикация, снятие с публикации;
  - пагинация, страница объявления;
  - бейдж непрочитанных.
- Документы:
  - категории;
  - загрузка в хранилище с проверкой типа по содержимому, лимит 20 МБ (в том числе в Caddy);
  - уровни доступа PUBLIC / OWNERS / PRIVATE;
  - скачивание через presigned URL.
- SEO-теги, `hreflang`, `robots.txt`, `sitemap.xml`.

Решения (ТЗ v1.9):
- на главной — 3 последних объявления и блок контактов;
- текст объявлений — Markdown без HTML;
- `send_push` хранится, флажок в форме — на этапе 6;
- дашборд — на этапе 5;
- presigned URL ведёт на домен сайта, Caddy проксирует `/files/*` в хранилище;
- объявления рендерятся динамически, без revalidate;
- тестовый API сдвигает часы API для проверки отложенной публикации;
- документы OWNERS станут доступны пользователям помещений на этапе 4.

Проверка:
- Автоматически:
  - e2e: объявление с датой в будущем не видно, а после наступления даты появляется (тест подменяет дату через тестовый эндпоинт, доступный только в dev);
  - закреплённое всегда первое;
  - документ PRIVATE: гостю — 404, админу — скачивается;
  - файл 21 МБ отклоняется;
  - `.exe`, переименованный в `.pdf`, отклоняется.
  - телефоны в контактах ведут на `wa.me/<номер>`; кнопка канала без ссылки не показывается; ссылка на чужой домен отклоняется.
- Вручную:
  - скачанный файл открывается;
  - после удаления документа объект исчез из хранилища (интерфейс filer);
  - тексты на трёх языках, все переводы обязательны в формах.

### Этап 4. Помещения, собственники, импорт (L)
**Цель:** реестр помещений и собственников в системе, первичная загрузка из CSV.

Задачи:
- Модели `Unit`, `Owner`, `UnitOwnership`, `UnitDocument`.
- Разделы `/admin/units` и `/admin/owners`:
  - поиск, фильтры, натуральная сортировка;
  - доли, контактное лицо, «нет контакта» — только для чтения: помещения и собственников меняет только импорт (ТЗ v1.12);
  - вручную — категория тарифа квартиры, документы помещения, заметка о собственнике;
  - привязка и создание учётной записи.
- Импорт `registry.csv` — помещения и собственники одним файлом, телефон собственника (ТЗ v1.13):
  - предпросмотр с ошибками;
  - сопоставление по номерам документов;
  - разбор неоднозначных совпадений;
  - идемпотентность.
- Шифрование и доступ к `id_numbers`: только ADMIN, не попадают в API жильцов и экспорт.
- Личный кабинет:
  - список помещений пользователя через собственников, переключение;
  - совладельцы без телефонов;
  - отображаемое имя;
  - документы помещения.
- Документы OWNERS становятся доступны пользователям помещений.
- Генератор: полный набор 312 помещений и собственников.

Решения (ТЗ v1.10):
- импорт обновляет существующие помещения и доли по файлу, ничего не удаляет;
- похожие имена (другой порядок слов, опечатка) — неоднозначные совпадения на ручной разбор;
- один номер документа у разных `owner_key` — ошибка файла;
- один ключ в окружении для шифрования и HMAC номеров документов;
- баланс — на этапе 5, синхронизация и контакты — на этапе 7; отдельного объединения помещений нет — объединение приходит со свежей выпиской (ТЗ v1.11);
- документы OWNERS видят пользователи с действующим помещением.

Проверка:
- Автоматически:
  - импорт синтетических CSV → ровно 312 помещений, распределение по видам совпадает;
  - повторный импорт ничего не меняет;
  - дубли и однофамильцы попадают в отчёт, а не в БД;
  - IDOR-тесты: жилец не видит чужое помещение и чужой документ (404), `id_numbers` нет в ответах `/api/me/*`.
- Вручную:
  - разбор спорных совпадений в предпросмотре;
  - помещение юрлица в кабинете его представителя;
  - сортировка: 5, 5ა, 5ბ, 6…

### Этап 5. Финансы (L)
**Цель:** тарифы, начисления, операции, услуги, личный кабинет с балансом.

Задачи:
- Модели `Tariff`, `BalanceTransaction`, `TransactionAttachment`, `PaidService`.
- Операции по помещению:
  - ежемесячное начисление, услуга, оплата, входящий остаток (документ обязателен), корректировка;
  - атомарное изменение баланса;
  - неизменяемость операций.
- Тарифы с историей:
  - ставки для квартир по категориям и для паркинга;
  - необязательные ставки для коммерческих и технического помещений.
- Массовое начисление:
  - ручное;
  - автоматическое через `pg-boss` 1-го числа в 00:10 Asia/Tbilisi;
  - защита от дублей уникальным индексом;
  - начисление новому помещению за текущий месяц.
- Услуги: `/admin/services`, публичная страница с ISR и персональной ценой.
- История операций, фильтры, экспорт CSV (UTF-8 BOM, `;`), сверка балансов.
- Личный кабинет: баланс с цветом, история с пагинацией, документы к операциям.
- Дашборд: задолженность, должники, последнее автоначисление.

Проверка:
- Автоматически:
  - модульные тесты расчётов: категории, паркинг, пустые ставки у коммерческих и технического, выбор тарифа на дату, границы месяца в Asia/Tbilisi;
  - интеграционный тест: два параллельных «Начислить всем» → ровно одно начисление на помещение;
  - сверка балансов после серии операций — расхождений нет;
  - e2e: полный цикл «начисление → оплата → корректировка» с проверкой баланса в кабинете жильца.
- Проверка автоначисления в контейнере:
  - запуск задачи через dev-эндпоинт с подменой даты;
  - проверка расписания: в `worker` задаётся частое cron-выражение через переменную окружения, затем `make restart` — задача срабатывает и не дублируется.
- Вручную:
  - CSV-экспорт открывается в Excel без «кракозябр»;
  - персональная цена услуги в кабинете.

### Этап 6. PWA и push-уведомления (M)
**Цель:** подписка на уведомления, рассылки, push об операциях.

Задачи:
- Manifest, иконки, service worker (`/sw.js` в корне), установка на домашний экран.
- VAPID-ключи в `.env`, подписки устройств, настройки в `/account/notifications`.
- Модели `Notification`, `NotificationRecipient`. Отправка через очередь в `worker`, удаление протухших подписок.
- Push:
  - о новых объявлениях (в том числе отложенных);
  - об операциях по балансу;
  - ручные рассылки по языковым группам.
- История рассылок в `/admin/notifications`.

Проверка:
- Автоматически:
  - интеграционные тесты очереди с фейковым push-сервисом: статусы SENT / PARTIAL / FAILED / NO_SUBSCRIPTION / SKIPPED;
  - ответ 410 удаляет подписку;
  - перезапуск `worker` посреди рассылки не теряет и не дублирует сообщения.
- Вручную:
  - Chrome и Firefox на `https://localhost`: подписка, получение, клик открывает нужную страницу;
  - **телефон** (Android Chrome, iPhone с сайтом на экране «Домой»): нужен доверенный HTTPS. Варианты — туннель (`cloudflared` / `ngrok`) или установка корневого сертификата Caddy на телефон;
  - массовое начисление на 312 помещений → push приходят, админка отзывчива.

### Этап 7. Синхронизация с выпиской и учётные записи по телефонам (M)
**Цель:** периодическое обновление собственников и выдача доступа по телефонам из выписки.

Задачи:
- Синхронизация:
  - сравнение нового `registry.csv` с текущими данными;
  - экран различий;
  - построчное подтверждение;
  - смена собственника с сохранением баланса и отзывом доступа у прежнего;
  - выбывшие помещения → `ARCHIVED`, предупреждение о ненулевом балансе.
- Учётные записи по телефонам собственников из `registry.csv`: создание и поиск, привязка к собственникам, одноразовый файл с временными паролями.

Проверка:
- Автоматически:
  - синтетическая «новая выписка»: продажа, дарение с изменением долей, объединение двух квартир с новым кадастровым кодом (старые → `ARCHIVED`, новое создано);
  - различия показаны верно;
  - после применения баланс остался за помещением, а пользователь прежнего собственника получает 404 на помещение;
  - повторное применение ничего не меняет.
- Вручную:
  - файл с временными паролями скачивается один раз;
  - вход по временному паролю, смена пароля.

### Этап 8. Подготовка к запуску (M)
**Цель:** надёжность, безопасность, восстановление.

Задачи:
- Бэкапы: сервис `backup` (restic) — ежедневно `pg_dump` + бакеты хранилища, хранение 30 дневных и 12 месячных копий, `restic check`, push админам при ошибке. Локально копии пишутся в папку, в продакшене — в Backblaze B2.
- Runbook восстановления.
- `docker-compose.prod.yml`:
  - без dev-портов и bind-mount;
  - лимиты ресурсов;
  - `restart: unless-stopped`;
  - ротация логов.
- Заголовки безопасности (CSP, HSTS и др.) в Caddy.
- Проверка доступности: axe в Playwright на ключевых страницах.
- Полнота AuditLog по списку из п. 12 ТЗ.
- Нагрузочный smoke: 312 помещений, несколько лет операций, проверка скорости ключевых страниц.
- README и инструкция администратора.
- `ENABLE_TEST_API=false` в prod-оверлее: `/api/test/*` отвечает 404.
- Вычитка грузинских текстов интерфейса носителем языка (`apps/web/messages/ka.json`).

Проверка (**учения по восстановлению**):
1. `make up` на prod-конфигурации, загрузка данных, `make backup`.
2. `make reset` — всё удалено.
3. `make restore` из копии.
4. Сверка: число помещений, балансы, файлы документов, вход пользователей.

Дополнительно:
- axe без критичных нарушений;
- заголовки безопасности на месте;
- все e2e предыдущих этапов зелёные на prod-конфигурации.

---

### Этап 9. Развёртывание (S)
**Цель:** запуск на сервере после успешного локального тестирования.

Задачи:
- Покупка сервера и домена, DNS.
- Тот же `docker-compose` с prod-оверлеем и боевым `.env`; Caddy с Let's Encrypt.
- Бэкапы в Backblaze B2, ключ restic передан председателю и администратору.
- **До загрузки реальных данных:** получить заключение юриста по хранению номеров документов собственников (разд. 14 ТЗ). Если хранить нельзя — столбец `id_numbers` при импорте не заполняется.
- Загрузка реальных данных:
  - `registry.csv` из выписки, с телефонами из документа ТСЖ;
  - тариф;
  - входящие остатки.
- Учётные записи по телефонам собственников.

Проверка:
- `make smoke` против боевого домена;
- e2e-сценарии только на чтение;
- первое учение по восстановлению на сервере в отдельном каталоге;
- push на реальных телефонах.

---

### Этап 10. После запуска
- SMS-провайдер и восстановление пароля по SMS-коду (п. 5.6 ТЗ).
- Голосования (разд. 15 ТЗ) — после решения юриста.
- **Идея: синхронизация баланса и начислений с управляющей компанией.** Сейчас начисления и оплаты ведутся в системе вручную (этап 5). Если у управляющей компании есть свои данные по помещениям, их можно подтягивать автоматически, а не вводить повторно.
  - Первый шаг — разобрать, какие запросы делает приложение управляющей компании: адреса, авторизация, формат данных (начисления, оплаты, баланс по помещению), как помещения идентифицируются (номер, кадастровый код, лицевой счёт).
  - По итогам решить: импорт по расписанию или выгрузка по кнопке; кто источник истины для баланса; как сопоставлять операции, чтобы не задвоить начисления и оплаты.
  - Использование их API согласовать с управляющей компанией.

Каждый пункт — отдельный этап с той же процедурой приёмки (разд. 1).
