# Этап 0: сверка модели данных с выпиской из Публичного реестра

> **Статус: схема утверждена 27.10.2026** и внесена в ТЗ v1.5. Решения — в разд. 8.

Источник: полная выписка из Публичного реестра (НАПР) по участку 05.30.39.005 от 08.10.2026, 56 страниц.

> В этом документе намеренно нет персональных данных из выписки: ФИО, личных номеров, номеров паспортов. Саму выписку не следует класть в git-репозиторий. В системе её место — приватный документ (п. 4.9 ТЗ).

## 1. Структура выписки

| Блок | Содержание | Нужно системе |
|---|---|---|
| Шапка | Кадастровый код участка, адрес, площадь участка 3149 м², здание N1 «строящееся» | Нет (справочно) |
| «მესაკუთრეები» — собственники | Сводный список всех собственников: имя + `P/N` (личный номер) и/или `C/N` (номер документа), для юрлиц — `ID` | Да — идентификация собственников |
| «ბინა ერთეულის მესაკუთრეები» — помещения | По каждому помещению: кадастровый код, собственник(и), вид собственности, тип помещения, этаж, номер, площадь, документы-основания | Да — основной источник |
| «იპოთეკა» — ипотека | Обременение участка 2016 года (договор застройщика) | Нет |

### 1.1 Кадастровый код помещения
```
05.30.39.005 . 01 . XX . NNN
участок      здание раздел номер
```
| Раздел `XX` | Вид | Номера `NNN` |
|---|---|---|
| `01` | Квартиры и техническое помещение | 001–257, 005ა–005დ, 500, 502 |
| `02` | Паркинг (ავტოსადგომი) | 001–047 |
| `03` | Коммерческие помещения (კომერციული ფართი) | 001–005 |

### 1.2 Поля помещения
- **Кадастровый код** — уникален. Лучший естественный ключ для импорта и повторной сверки.
- **Собственник(и):** физлица или юрлица. Указано **только имя на грузинском**, без личного номера: номера есть только в сводном списке.
- **Вид собственности:**
  - `საკუთრება` — единоличная;
  - `თანასაკუთრება` — совместная/долевая, иногда с долями: `50%`, `1/6`, `4/6`, `1/2`, `1/4`.
- **Тип:** ფართი (площадь), ტექნიკური ფართი (техническая), ტერასა (терраса), ავტოსადგომი (машиноместо), კომერციული ფართი (коммерческая). Все помещения помечены «строящееся».
- **Этаж:** 1–20 для жилых и коммерческих; `-3` для паркинга; «технический этаж (отм. 65.10)».
- **Номер:** `N1`…`N257`, а также номера с грузинскими буквами: `5ა`, `5ბ`, `5გ`, `5დ`.
- **Площадь, м².**
- **Основания** (договоры купли-продажи, дарения, наследство) — системе не нужны.

## 2. Состав помещений

| Вид | Кол-во | Площадь | Примечание |
|---|---|---|---|
| Квартиры | **259** | 30.08 – 636.17 м² | Совпадает с заявленным числом |
| Машиноместа | **47** | 13.75 / 16.25 м² | Совпадает с заявленным числом |
| Коммерческие | **5** | 174.72 – 286.72 м² | 1-й этаж |
| Техническое | **1** | 338.99 м² + терраса 403.63 м² | Одно помещение из двух частей, **в частной собственности** |
| **Итого** | **312** | | |

Как получаются 259 квартир: коды 001–257 (257 шт.) без отсутствующих 133, 228, 229 (−3), плюс 005ა, 005ბ, 005გ, 005დ (+4), плюс код 502 = квартира N228 (+1).

### 2.1 Объединённые квартиры
Объединения в реестре уже отражены, и это подтверждает правило «помещение = юридическая единица».
- **Код 502 — квартира «N228», 122.34 м².** Кодов 228 и 229 нет, значит это объединённые 228+229, которые получили **новый кадастровый код**.
- **Код 132 — квартира N132, 109.80 м²** (типовая квартира на этаже — около 74 м²). Кода 133 нет, вероятно это объединённые 132+133 под **старым кодом**. Нужно подтвердить.

Вывод для модели: номер квартиры и кадастровый код не совпадают, хранить нужно оба.

### 2.2 Квартиры 2-го этажа с литерами
`5ა` (128.49 м²), `5ბ` (636.17 м²), `5გ` (209.47 м²), `5დ` (265.73 м²) — большие помещения. Номер содержит грузинскую букву, поэтому:
- номер хранится строкой как в реестре;
- для сортировки нужен отдельный ключ: число + суффикс;
- для отображения на ru/en нужна транслитерация (5ა → 5а / 5a).

## 3. Собственники

### 3.1 Типы
- **Физлица** — подавляющее большинство, много иностранцев.
- **Юрлица** — 2 компании (ООО, `შპს`), одна из них — застройщик. Юрлицу принадлежат **15 помещений**: 8 квартир, 5 машиномест, 2 коммерческих.

### 3.2 Совместная и долевая собственность
- **16 помещений** с несколькими собственниками.
- В 3 из них указаны доли. Есть сложный случай: доля 1/4 принадлежит совместно двум лицам — то есть доля внутри доли.
- **Голосование:** по-прежнему один голос на помещение. Доли важны только для отображения и, возможно, для правил голосования (решение юриста).

### 3.3 Качество данных — существенные проблемы
1. **Дубли в сводном списке.** Одно лицо записано несколько раз (до 5) с разным написанием имени. Пример паттерна: «Имя Фамилия», «Фамилия Имя» и вариант с опечаткой — все с одним номером документа. Компания тоже записана дважды («შპს შპს …» и «შპს "…"») с одним ID.
2. **Номера перепутаны.** Встречается:
   - `P/N` и `C/N` переставлены местами;
   - в поле `P/N` записан номер паспорта;
   - в одном поле несколько номеров через `;` или `/`.
3. **Разные форматы номеров:**
   - грузинский личный номер — 11 цифр;
   - паспорта РФ — `NN NNNNNNN`, с пробелом и без;
   - белорусские, латвийские, украинские, израильские и другие.
4. **Помещения связаны с собственниками только по имени.** В блоке помещений номера документов не указаны. Поэтому:
   - совпадение имени при разном написании нужно находить нечётким сравнением;
   - **однофамильцы неразличимы:** в выписке есть два одноимённых лица с разными паспортами и два почти одноимённых. Каким из них принадлежит помещение, по выписке не установить — нужна ручная проверка.
5. **Имена только грузинским письмом.** Для интерфейса на русском и английском нужно отображаемое имя, которое внесёт ТСЖ или сам собственник.
6. **Телефонов в выписке нет.** Контакты придётся собирать отдельно.

### 3.4 Изменения собственников
В выписке много сделок 2025–2026 годов, в том числе за последние недели до даты выписки. Собственники будут меняться регулярно. Нужен механизм повторной сверки с новой выпиской (п. 5.3).

## 4. Расхождения с текущей моделью (ТЗ v1.4)

| # | Текущая модель | Факт из выписки | Изменение |
|---|---|---|---|
| 1 | Собственник = `User` (логин по телефону) | Собственник — лицо из реестра, телефона нет. У юрлица логина нет вовсе | Разделить: **`Owner`** (собственник по реестру) и **`User`** (учётная запись). Собственник может существовать без учётной записи и всё равно получает начисления и голос |
| 2 | `UnitOwner.is_primary` | Совместная и долевая собственность с долями | `UnitOwnership.share` (дробь, nullable) + `share_note` для сложных случаев |
| 3 | `kind`: APARTMENT / PARKING / COMMERCIAL / TECHNICAL | Подтверждено. Техническое помещение одно и частное | Без изменений |
| 4 | `cadastral_code` nullable | Есть у каждого помещения, уникален | Сделать **обязательным и уникальным**; это ключ импорта |
| 5 | `number` — строка | Номера с грузинскими буквами, номер ≠ код | `number` как в реестре + `sort_key` |
| 6 | `floor` Int | Есть «технический этаж (отм. 65.10)» | `floor` Int nullable + `floor_label` (nullable) |
| 7 | Площади нет | Площадь есть у всех, разброс 13.75 – 636 м² | Добавить `area_m2` |
| 8 | — | Юрлица | `Owner.kind` = PERSON / COMPANY, `company_code` |
| 9 | — | Нужна идентификация при импорте и повторных сверках | `Owner.id_numbers` — нормализованные номера документов, видны только администратору (см. вопрос 4) |

## 5. Предлагаемая схема (на утверждение)

### 5.1 Unit — помещение
```
id                UUID, PK
kind              Enum: APARTMENT | PARKING | COMMERCIAL | TECHNICAL
cadastral_code    String, UNIQUE           — например 05.30.39.005.01.01.045
number            String                   — как в реестре: «45», «5ა», «228», «P-12»
sort_key          String                   — для натуральной сортировки (раздел + число + суффикс)
floor             Int (nullable)           — -3 для паркинга
floor_label       String (nullable)        — «тех. этаж (отм. 65.10)»
area_m2           Decimal(8,2)
tariff_category   Enum TariffCategory (nullable) — для квартир
balance           Decimal(10,2)
status            Enum: ACTIVE | MERGED
merged_into_id    UUID → Unit (nullable)
created_at        DateTime
```

### 5.2 Owner — собственник по реестру (новая таблица)
```
id              UUID, PK
kind            Enum: PERSON | COMPANY
registry_name   String               — имя как в выписке (грузинским письмом)
display_name    String (nullable)    — имя для интерфейса (латиница/кириллица), вносит ТСЖ или сам собственник
id_numbers      String[]             — нормализованные личные номера / номера документов / ID компании (только для ADMIN)
user_id         UUID → User (nullable) — учётная запись, через которую собственник пользуется сайтом
note            String (nullable)
created_at      DateTime
updated_at      DateTime
```
- У физлица `user_id` — его собственная учётная запись. У юрлица — учётная запись представителя.
- Одна учётная запись может быть привязана к нескольким `Owner`. Например, представитель компании, который сам тоже собственник.

### 5.3 UnitOwnership — право собственности (вместо UnitOwner)
```
id            UUID, PK
unit_id       UUID → Unit
owner_id      UUID → Owner
share_num     Int (nullable)         — числитель доли
share_den     Int (nullable)         — знаменатель доли
share_note    String (nullable)      — сложные случаи («1/4 совместно с …»)
is_contact    Boolean                — основное контактное лицо по помещению
UNIQUE (unit_id, owner_id)
```

### 5.4 User — учётная запись
Без изменений: телефон, пароль, роль, язык, настройки уведомлений. Поле `full_name` убирается — имя берётся из связанного `Owner.display_name`. У администраторов без собственности — своё поле `name`.

### 5.5 Что меняется в логике
- **Доступ в личный кабинет:** пользователь видит помещения всех `Owner`, у которых `user_id` = он сам.
- **Push об операциях:** получают пользователи, связанные с собственниками помещения.
- **Голосование:** один голос на помещение. Голосует любой из пользователей, связанных с собственниками помещения (правило для совладельцев — по решению юриста).
- **Начисления и баланс** — по помещению, как раньше. При смене собственника долг остаётся за помещением.
- **Должник без учётной записи** виден администратору как «нет контакта».

## 6. Импорт

### 6.1 Шаг 1 — помещения и собственники из выписки
PDF выписки — HTML-страница, распечатанная в PDF. Текст извлекается, но вёрстка «плывёт»: переносы, имя и тип в одной строке. Надёжного автоматического парсера для повторяемого использования это не даёт. Поэтому предлагаю так:

1. **Разовая конвертация** выписки в два CSV: `units.csv` и `owners.csv`.
   - Скрипт и ручная вычитка: дубли, однофамильцы, перепутанные номера.
   - CSV хранятся вне git (папка `data/` в `.gitignore`): в них персональные данные.
2. **Импорт CSV в админке** (п. 8.10 ТЗ, формат расширяется):
   - `units.csv`: cadastral_code, kind, number, floor, floor_label, area_m2, tariff_category;
   - `owners.csv`: owner_key, kind, registry_name, id_numbers, cadastral_code, share, is_contact.
3. **Отчёт о спорных строках.** Однофамильцы и неоднозначные совпадения не импортируются, пока администратор не разрешит их вручную.

### 6.2 Шаг 2 — контакты
Отдельный CSV от ТСЖ: `cadastral_code` или `owner_key`, телефон, язык, отображаемое имя. По нему создаются учётные записи `User` и привязываются к `Owner`. Временные пароли выдаются так же, как в п. 8.10.

### 6.3 Повторная сверка с новой выпиской
Новая выписка конвертируется в те же CSV. Система показывает разницу:
- новые и выбывшие собственники;
- изменения долей;
- новые и исчезнувшие помещения (объединения).

Администратор подтверждает изменения. Баланс остаётся за помещением. Учётная запись бывшего собственника отвязывается от помещения, всё пишется в AuditLog.

## 7. Вопросы для утверждения схемы

1. **Разделение «собственник по реестру» и «учётная запись»** (`Owner` / `User`). Подтверждаете? Без этого не получится корректно учесть юрлица, совладельцев без телефона и смену собственников.
2. **Начисление при разной площади.** Квартиры от 30 до 636 м² (5ბ), коммерческие — 175–287 м². Остаётся фиксированная ставка по категории или нужна ставка за м²? Площадь в модели будет в любом случае.
3. **Коммерческие помещения (5) и техническое (1, частное):** начисляется ли взнос и по какой ставке? Дают ли голос?
4. **Личные номера и номера паспортов.** Хранить в системе (только для администратора, нужны для сверки с новыми выписками) или использовать только при импорте и не сохранять? Рекомендую хранить: без них повторная сверка ненадёжна.
5. **Квартира N132 (109.80 м²)** — это объединение 132+133? В выписке нет кода 133.
6. **Помещения юрлица (15 шт.):** кто контактное лицо и куда направлять начисления?
7. **Повторная сверка с новой выпиской** (п. 6.3) — нужна к запуску или позже? Рекомендую к запуску: сделки идут постоянно.
8. **Конвертация выписки в CSV** (п. 6.1) — сделать мне? Результат положу в `data/` вне git, спорные места отмечу для ручной проверки.
