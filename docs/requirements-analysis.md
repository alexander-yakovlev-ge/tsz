## 1. Краткое резюме

ТЗ в целом проработано хорошо: есть модель данных, роли, список страниц и API, требования безопасности. Однако перед стартом разработки нужно закрыть несколько **блокирующих** вопросов — в первую очередь по финансовой логике:

1. **Непонятен смысл знака баланса и начислений** — нет типа операции «оплата», а «начисление» увеличивает баланс (см. 2.1).
2. **Защита от двойного начисления не реализуема на текущей модели** — у транзакции нет поля периода (см. 2.2).
3. **Лимиты SMS посчитаны неверно** — кириллица и грузинский идут в UCS-2, то есть 70 символов, а не 160 (см. 5.1). Это напрямую влияет на стоимость рассылок.
4. **Несколько сущностей, упомянутых в функционале, отсутствуют в модели**: категории документов, мягкое удаление пользователей, прочтение объявлений, статус рассылки, журнал аудита (см. 3).

## 2. Финансовая логика — критичные вопросы

### 2.1 Знак суммы и смысл «начисления»

- п. 4.5: «положительное = начисление, отрицательное = списание».
- п. 7.2: зелёный при `> 0`, красный при `< 0` — то есть отрицательный баланс = долг.
- п. 8.1: «+Ежемесячный» **увеличивает** баланс, «−Услуга» уменьшает.

Если «ежемесячный платёж» — это обязательство жильца (долг перед ТСЖ), то он должен **уменьшать** баланс, а не увеличивать. При текущей формулировке массовое «Начислить всем» делает всех «зелёными», а должников не появится никогда — что противоречит п. 8.1 «сортировка по балансу для выявления должников».

Возможны две интерпретации — нужно выбрать одну:

| Вариант | MONTHLY_CHARGE | Оплата жильца | Услуга |
|---|---|---|---|
| **А. Лицевой счёт (рекомендуется)** | `−сумма` (долг) | `+сумма`, новый тип `PAYMENT` | `−цена` |
| Б. Предоплатный кошелёк | `+сумма` = фиксация факта оплаты ежемесячного взноса | — | `−цена` |

В варианте Б кнопка «Начислить всем» не имеет смысла (нельзя массово зафиксировать оплату за всех). Поэтому вариант А выглядит правильным, но тогда:

- нужен тип транзакции **`PAYMENT`** (сейчас оплату можно провести только через `CUSTOM`, что ломает отчётность);
- кнопки в п. 8.1 надо переименовать/перезнаковать: «−Ежемесячный», «−Услуга», «+Оплата», «Корректировка».

### 2.2 Защита от двойного начисления

У `BalanceTransaction` нет поля периода — проверить «было ли начисление за октябрь 2026» можно только эвристикой по `created_at`, что ненадёжно (начисление за октябрь может быть сделано 2 ноября).

Предложение:

- добавить поле `period` (`DATE`, первое число месяца) для `MONTHLY_CHARGE`;
- уникальный индекс `(apartment_id, period) WHERE type = 'MONTHLY_CHARGE'`;
- **одиночная кнопка «+Ежемесячный» (п. 8.1) тоже должна требовать выбора периода** и подпадать под ту же защиту — иначе она обходит защиту массового начисления;
- массовое начисление выполнять в одной транзакции БД, пропуская квартиры, у которых начисление за период уже есть, и показывать их в отчёте.

### 2.3 Какой тариф применять

- «Текущий активный тариф» = запись `Tariff` с максимальным `effective_from ≤ now()` — стоит явно зафиксировать в ТЗ.
- Для начисления **за период** правильнее брать тариф, действующий на начало этого периода, а не на сегодня (иначе начисление «задним числом» после повышения тарифа даст неверную сумму).
- Поле `Tariff.name` есть в модели, но отсутствует в форме п. 8.3 — либо убрать, либо добавить в форму.
- Нужен часовой пояс для границ месяца и `effective_from` — предлагается `Asia/Tbilisi`.

### 2.4 Хранение баланса

`Apartment.balance` — денормализованное поле рядом с журналом транзакций. Требования к реализации:

- любое изменение баланса — только в одной БД-транзакции вместе с созданием `BalanceTransaction` (атомарный `UPDATE ... SET balance = balance + :amount`);
- транзакции **неизменяемы**: ошибки исправляются только сторнирующей операцией (`CUSTOM` с комментарием). Это стоит явно записать в ТЗ — сейчас ни редактирование, ни удаление транзакций не описано;
- периодическая сверка `balance = SUM(amount)` (можно в виде скрипта/проверки в админке).

### 2.5 Прочее

- Валюта (вопрос 13.1): по контексту однозначно GEL; хранить `Decimal(10,2)`, в коде — без `float`.
- `SERVICE_DEBIT` сохраняет сумму на момент списания — это правильно, т. к. цена услуги может меняться. FK `service_id` — с `ON DELETE RESTRICT` (согласуется с п. 8.4 «удаление только без транзакций»).
- Именование: поле `Apartment.tariff` (категория FULL/BLACK_FRAME/PENSIONER) и модель `Tariff` (прайс) — путаница. Предлагается enum `TariffCategory` и поле `Apartment.tariff_category`.

## 4. Аутентификация и роли

- **Роли.** Председатель/админ почти наверняка сам собственник квартиры. Сейчас `/account` доступен «только RESIDENT» (п. 7) — админ не увидит свой баланс. Предлагается: личный кабинет доступен любому авторизованному пользователю с привязанными квартирами, админка — только ADMIN.
- **Конфликт маршрутов.** NextAuth занимает `/api/auth/*` (catch-all `[...nextauth]`). Эндпоинты `/api/auth/login`, `/api/auth/logout` из п. 9 дублируют встроенные `signin/signout`, а `/api/auth/change-password` придётся аккуратно размещать рядом с catch-all. Предлагается: вход/выход — средствами NextAuth, смена пароля — `/api/me/password`.
- **«Access-токен 24 ч + автообновление»** (п. 5.5) в NextAuth реализуется как скользящая JWT-сессия (`maxAge` + `updateAge`), отдельных refresh-токенов нет — сформулировать требование именно так.
- **Rate limiting** (10 попыток / 15 мин с IP): на одном VPS достаточно in-memory или хранения в PostgreSQL; за reverse-proxy обязательно корректно брать IP из `X-Forwarded-For`. Дополнительно рекомендуется лимит на номер телефона (защита от перебора пароля конкретного жильца с разных IP).
- **CSRF** (п. 11): Server Actions в Next.js проверяют Origin автоматически; для Route Handlers — cookie `SameSite=Lax` + проверка заголовка `Origin`. Отдельные CSRF-токены не нужны.
- **Восстановление пароля.** Самостоятельного сброса нет — только через админа. При наличии SMS-провайдера логично добавить сброс по SMS-коду (вопрос заказчику, можно во вторую очередь).
- **Формат телефона** (вопрос 13.5): нормализация в E.164 через `libphonenumber-js`, регион по умолчанию — GE (номер `555 12 34 56` → `+995555123456`). Иностранные номера поддерживаются тем же кодом, если ввести с `+`. Важно для Батуми — много собственников-иностранцев.

## 5. SMS-рассылка → push-уведомления

> **Решение:** SMS, скорее всего, не используются. Основной канал — Web Push. Разделы 5.1–5.2 оставлены для истории, на случай если SMS понадобятся как резервный канал.

### 5.0 Web Push: что учтено в ТЗ v1.1

- **Технология.** Стандартный Web Push (VAPID, библиотека `web-push`) без Firebase и внешних сервисов. Сайт оформляется как PWA: manifest и service worker.
- **iOS.** Push работает только у сайта, установленного на экран «Домой» (iOS 16.4+). В ЛК нужна инструкция, иначе заметная часть жильцов на iPhone не подпишется.
- **Охват.** В отличие от SMS, push получают только те, кто сам подписался. Поэтому в форме рассылки показывается, сколько выбранных получателей без подписки. Для таких людей важное всё равно должно быть видно на сайте: объявления с бейджем непрочитанных.
- **Связь с объявлениями.** Типичный сценарий — «опубликовал объявление → уведомил». В форму объявления добавлен флаг «Отправить push». Для отложенных объявлений push уходит отложенной задачей `pg-boss` в момент публикации.
- **Модель.** `PushSubscription` (несколько устройств на пользователя), `Notification` + `NotificationRecipient` вместо `SmsLog` + `SmsRecipient`.
  - У получателя есть статусы `NO_SUBSCRIPTION` / `SKIPPED`.
  - Подписки, на которые push-сервис ответил 404/410, удаляются.
- **Статус доставки.** Push-сервисы его не дают: `SENT` = «принято push-сервисом». Если нужна статистика, можно позже отслеживать клики через `notificationclick`.
- **Лимиты.** Ограничения в 70/160 символов нет. Есть рекомендуемая длина, иначе ОС обрезает текст: заголовок до ~50, текст до ~150 символов. Payload не больше ≈ 4 КБ.
- **Очередь** нужна по-прежнему: `pg-boss` + воркер.

### 5.1 Неверные лимиты символов

П. 8.8: «160 символов для латиницы/кириллицы, 70 для юникода». На практике:

| Текст | Кодировка | 1 SMS | Каждая часть составного SMS |
|---|---|---|---|
| Латиница (только GSM-7) | GSM-7 | 160 | 153 |
| **Кириллица** | UCS-2 | **70** | 67 |
| **Грузинский** | UCS-2 | **70** | 67 |

Т. е. для двух из трёх языков лимит — 70. Счётчик должен определять кодировку по фактическому тексту и показывать **количество сегментов** — стоимость рассылки считается по сегментам. В подтверждении «Будет отправлено N сообщений» лучше показывать и число SMS-сегментов.

### 5.2 Прочее

- **Очередь** (п. 8.8 «асинхронная отправка») — в стеке её нет. Рекомендуется `pg-boss` (очередь поверх PostgreSQL, без лишнего Redis) и отдельный воркер-контейнер в Docker Compose.
- **«Статус доставки»** (история рассылок) требует приёма DLR-вебхуков от провайдера; без них есть только «отправлено/ошибка API». Уточнить, что именно нужно.
- **Провайдер.** Для грузинских номеров дешевле и надёжнее локальный (Magtifun / smsoffice.ge и т. п.); нужна регистрация имени отправителя (Sender ID). Интерфейс провайдера абстрагировать — выбор можно отложить.
- **«Все собственники»** — уточнить: пользователи, привязанные хотя бы к одной квартире, не удалённые; один номер = одно сообщение, даже если у человека несколько квартир.
- Пользователи без указанного языка получают `ka` (дефолт из модели). Если для языковой группы текст не заполнен — эта группа не получает сообщение; в подтверждении явно показать, сколько человек будет пропущено.

## 6. Публичная часть и кэширование

- **ISR и персонализация конфликтуют.** Страница «Услуги» кэшируется ISR (п. 12), но авторизованный жилец должен видеть свою цену (п. 6.4). Решение: статическая часть (список, цены по трём категориям) — ISR, персональное выделение «ваша цена» — на клиенте через `/api/me/apartments`.
- **Скачивание документов.** П. 6.3 допускает «прямую ссылку или проксирование», п. 11 требует presigned URL. Рекомендуется: кнопка «Скачать» ведёт на `/api/documents/:id/download`, который генерирует presigned URL и делает редирект. Так закэшированная ISR-страница не содержит протухающих ссылок.
- **Отложенная публикация объявлений** не требует cron — достаточно фильтра `published_at ≤ now()`, но страницу объявлений не стоит кэшировать дольше ~60 с.
- **Пагинация** публичного списка объявлений не описана — со временем список станет длинным.
- **Главная страница**, п. 6.2: «Войти / Личный кабинет» — также нужна ссылка «Админка» для ADMIN.
- **Публичная страница услуг**, п. 6.4: «редактирование — только для ADMIN» — уточнить, имеется ли в виду inline-редактирование на публичной странице или только через `/admin/services` (рекомендуется второе).

## 7. Мультиязычность

- Все маршруты из п. 10 фактически живут под префиксом `/[locale]/...`; middleware должен совмещать next-intl и проверку авторизации (редирект на `/{locale}/login`).
- Язык интерфейса (URL) и `User.language` (язык SMS) — разные вещи. Можно предлагать обновить `User.language` при смене языка интерфейса в ЛК или дать настройку в профиле — уточнить.
- В админ-формах с тремя языками: какие поля обязательны? Предлагается: `ka` обязателен, `ru`/`en` — с фолбэком на `ka` при отображении.
- Переводы нужны также для enum-значений (категории тарифа, типы транзакций), сообщений Zod-валидации и шаблонов SMS.
- SEO: `hreflang`-альтернативы для трёх языков, `<html lang>`.

## 8. Админ-панель — недостающее

- **Дашборд `/admin`** упомянут, содержимое не описано. Предложение: суммарный долг, число должников, последние операции, дата последнего массового начисления.
- **Страницы редактирования** отсутствуют в п. 10: `/admin/users/:id`, `/admin/announcements/:id`, `/admin/services/new`, `/admin/services/:id`. Либо явно оговорить, что это модальные окна.
- **Квартиры:** нет удаления квартиры и отвязки собственника; в таблице п. 8.1 столбцы «Собственники (ФИО + телефон)» и «Телефон» дублируют друг друга.
- **Пользователи:** при создании нет поля ФИО и языка, хотя они есть в модели и нужны для рассылки.
- **Первоначальная загрузка** (вопрос 13.3): для ~сотен квартир ручной ввод долгий — рекомендуется CSV-импорт квартир/собственников/начальных балансов (тип `CUSTOM` с комментарием «Входящий остаток»).
- **CSV-экспорт** (п. 8.9): UTF-8 с BOM и разделителем `;`, иначе Excel покажет грузинский/кириллицу кракозябрами.
- **Документы:** проверка типа файла по содержимому (magic bytes), а не только по расширению; лимит 20 МБ — также на уровне reverse-proxy (`client_max_body_size`).

| GET | `/api/transactions/export` | Экспорт CSV |
| GET | `/api/tariffs` | История тарифов |
| GET/POST/PUT | `/api/document-categories` | Управление категориями |
| GET | `/api/documents/:id/download` | Presigned-редирект |
| GET | `/api/admin/services`, `/api/admin/announcements` | Списки с неактивными / неопубликованными |
| GET | `/api/sms/recipients` | Кандидаты в получатели с языком |

Замечания:

- `GET /api/apartments/:id` и `GET /api/me/apartments/:id/balance` — обязательная проверка, что квартира принадлежит текущему пользователю (иначе IDOR: жилец перебором id видит чужие балансы).
- `POST /api/apartments/charge-all` — должен принимать `period` и быть идемпотентным.
- Если админка делается на Server Actions, большая часть «админских» REST-эндпоинтов не нужна как публичный API — стоит решить заранее (см. п. 10).

## 10. Рекомендации по стеку и архитектуре

- **Монолит на Next.js** (App Router + Server Actions + Route Handlers), без отдельного FastAPI/Node — для объёма проекта этого достаточно, меньше инфраструктуры.
- **Next.js 15**, **Prisma**, **Auth.js v5** (бывший NextAuth), **Zod**, **next-intl**.
- **Очередь SMS** — `pg-boss`, воркер отдельным процессом.
- **Файлы** — MinIO в том же Docker Compose (или Cloudflare R2 / Hetzner Object Storage, если не хочется самим бэкапить).
- **Docker Compose:** `app`, `worker`, `postgres`, `minio`, `caddy`/`nginx` (TLS через Let's Encrypt).
- **Бэкапы** (вопрос 13.7): ежедневный `pg_dump` + синхронизация бакета во внешнее хранилище, хранение 30 дней, периодическая проверка восстановления. Для финансовых данных это обязательно.
- **Тесты:** в первую очередь — финансовая логика (начисления, защита от дублей, расчёт цен по категориям) и проверки доступа.

## 12. Предлагаемые этапы

1. **Каркас:** проект, Docker Compose, Prisma-схема с правками из разд. 3, i18n, авторизация, seed (админ, контакты).
2. **Публичная часть:** главная, объявления, документы, услуги, контакты + соответствующие разделы админки.
3. **Финансы:** квартиры, пользователи, привязки, тарифы, транзакции, массовое начисление, личный кабинет, история и CSV-экспорт, CSV-импорт.
4. **Push-уведомления:** PWA, подписки в ЛК, очередь, воркер, рассылки и их история, push из объявлений.
5. **Финализация:** аудит-лог, rate limiting, SEO, доступность, бэкапы, деплой.

Этапы 1–3 — минимально полезный продукт; push можно запускать отдельно.
